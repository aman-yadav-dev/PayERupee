# ADR-001: Modular Monolith

**Context:** PayERupee needs high developmental velocity, extreme transactional integrity for financial primitives, and future scalability.
**Decision:** We adopt a strictly layered Modular Monolith via Next.js App Router API, enforcing separation of concerns purely via folder structure and domain borders, not physical microservices.
**Consequences:** Simplifies deployment and guarantees atomic DB transactions. Prevents distributed transaction headaches (Saga patterns, two-phase commits). We can split the monolith in Phase 10 if necessary.

---
# ADR-002: PostgreSQL & Prisma

**Context:** Financial systems require ACID guarantees and strong type-safety.
**Decision:** PostgreSQL for robust ACID compliance. Prisma as the ORM for extreme TypeScript type safety and built-in migration management.
**Consequences:** Hard reliance on relational concepts (no NoSQL). Prisma `Decimal` ensures float math is safely sidestepped.

# ADR-003: Double-entry Ledger

**Context:** We must never lose track of money, even if payouts fail.
**Decision:** Implemented a strict immutable double-entry ledger where every movement has identical debit and credit sums.
**Consequences:** Complete auditability. Wallets are essentially materialized views of the Ledger history.

---
# ADR-004: Optimistic Concurrency Control (OCC)

**Context:** High-velocity concurrent payouts can cause race conditions leading to negative wallet balances.
**Decision:** Used `version` incrementing in the Prisma `update` query to trap `P2025` errors.
**Consequences:** Prevents all race conditions without requiring slow, locking serial database queues.

---
# ADR-005: Payout State Machine

**Context:** Payouts bounce between network states.
**Decision:** Implemented strict transitions (`PENDING -> PROCESSING -> SUCCESS/FAILED/REVERSED`).
**Consequences:** Mathematical impossibility of double refunding or double deducting.

---
# ADR-006: Provider Abstraction

**Context:** We will use multiple payout partners over time (Razorpay, Cashfree).
**Decision:** Built `IPayoutProvider`. Core domain logic has zero knowledge of Razorpay API syntax.
**Consequences:** Swapping providers is purely an infrastructure task, not a domain rewrite.

---
# ADR-007: Provider Calls Outside DB Transactions

**Context:** Network calls during an open DB transaction exhaust connection pools and lock tables.
**Decision:** `payout.orchestrator.ts` strictly commits the `PROCESSING` state before `provider.dispatch()` is called.
**Consequences:** Eliminates Neon DB connection exhaustion. Leaves edge-case "Orphaned" payouts in `PROCESSING` if the network times out, which must be swept by a reconciliation worker later.

---
# ADR-008: Idempotency Strategy

**Context:** Merchants retry requests when networks fail.
**Decision:** API routes trap `P2002` Prisma unique constraint errors on `idempotencyKey` and instantly return `200 OK` with the existing payout.
**Consequences:** Safe retry mechanics without duplicate deductions.

---
# ADR-009: Webhook Security

**Context:** Forged webhooks could trick the system into refunding money.
**Decision:** Signatures must be verified via timing-safe cryptographic comparisons BEFORE any database lookups occur.
**Consequences:** Demands raw-body parsing capability from Next.js (Phase 5 requirement).

---
# ADR-010: Reconciliation Model

**Context:** The network is inherently unreliable. Webhooks drop.
**Decision:** We do not automatically refund on a timeout. A separate background cron will execute a provider `.status()` poll to reconcile aged `PROCESSING` payouts.
**Consequences:** Prevents catastrophic loss of funds to silent provider successes.

---
# ADR-011: Provider-Agnostic Architecture

**Context:** Hardcoding provider specifics leaks infrastructure into the domain.
**Decision:** Providers map their custom terminology back to our strict ENUMS.
**Consequences:** Domain remains pristine.

---
# ADR-012: No Premature Microservices

**Context:** Distributed architectures introduce extreme complexity for financial transactions.
**Decision:** We will not use microservices until CPU/Memory bounds demand it (Phase 10).
**Consequences:** Faster iteration, guaranteed atomicity, simpler infrastructure.
